# UI-PROD-00 — UI inventory & visual baseline

## Purpose

UI-PROD-00 establishes a reproducible **before** snapshot for the production UI hardening programme. It does not redesign screens, change business behaviour, or change the normal CenterManager startup path.

Baseline source revision:

`df39c7adcd3c896674163fb0ce95dc55abd135f2`

The task has two deliverables:

1. an exhaustive source inventory of screens/components and measurable visual-debt signals;
2. a repeatable visual-baseline recorder for the current desktop application.

## 1. Source inventory

Run from `CenterManager/`:

```bash
python scripts/ui_inventory.py --write
```

The scanner walks every Python module under `src/centermanager/ui` using the standard-library AST. It does **not** import application modules, so it does not need database fixtures, runtime configuration, login credentials, or a GUI.

Generated outputs:

- `docs/ui_baseline/UI_INVENTORY.md` — human-reviewable full list;
- `docs/ui_baseline/ui_inventory.json` — machine-readable full list.

To detect drift after a snapshot is generated:

```bash
python scripts/ui_inventory.py --check
```

### Classification

| Type | Meaning |
| --- | --- |
| `screen` | page/window/wizard level UI |
| `shell` | workspace shell / navigation container |
| `dialog` | modal or dialog-level UI |
| `component` | reusable/embeddable widget |
| `helper` | UI-owned non-widget helper class |

Every `screen`, `shell`, and `dialog` gets a stable screenshot baseline ID such as `student_workspace.student_list_page`.

### Visual-debt signals

The same scan records:

- count of `setStyleSheet(...)` calls;
- files containing raw hexadecimal colors;
- files importing legacy `centermanager.ui.styles`;
- files importing `centermanager.ui.design_system.tokens`;
- AST parse errors.

These numbers are a baseline, not a quality score. Later UI-PROD tasks can measure whether local styling and duplicate theme ownership are actually being reduced.

The exhaustive class list is generated by the scanner above. At product level, the current surface families are:

| Area | Current UI responsibility |

The generated inventory is authoritative when this summary and the source tree differ.

## 3. Screenshot baseline recorder

The screenshot implementation is intentionally a **separate development launcher**. `run.py`, `centermanager.app`, and normal production behaviour are not modified.

On a reference Windows workstation:

```bash
cd CenterManager
python scripts/ui_baseline_capture.py
```

Login normally, navigate to the desired screen/state, then press:

`Ctrl+Shift+B`

The recorder asks for a stable baseline ID and writes:

- `<id>__window.png` — full CenterManager window;
- `<id>__surface.png` — active page/workspace content;
- `manifest.json` — capture environment and widget metadata.

Default output:

`artifacts/ui-baseline/df39c7adcd3c/`

Override it when needed:

```powershell
$env:CENTERMANAGER_UI_BASELINE_DIR="D:\ui-baseline"
python scripts/ui_baseline_capture.py
```

Runtime screenshots are intentionally ignored by Git. They may contain real student/employee information and should be kept in approved review evidence storage rather than committed automatically.

## 4. Reference capture protocol

For comparable screenshots across UI-PROD phases:

1. capture the main baseline at **1920×1080 / Windows 100% scaling**;
2. do a separate smoke capture at 125% scaling where layout risk exists;
3. use deterministic/demo data where possible;
4. do not capture production PII into the repository;
5. capture important READ and EDITING permission/collaboration states separately;
6. use the same baseline IDs instead of creating ad-hoc filenames.

## 5. Verification

```bash
cd CenterManager
python -m pytest tests/test_ui_inventory_tool.py
python scripts/ui_inventory.py --write
python scripts/ui_inventory.py --check
```

The inventory tests assert that the scanner finds core application/workspace surfaces, preserves stable classification, and is deterministic.

## Acceptance criteria

- [x] Inventory scans every `ui/**/*.py` source file recursively.
- [x] Screens, shells, dialogs, reusable components and UI helpers are classified.
- [x] Stable screenshot IDs are generated for capture-worthy surfaces.
- [x] Visual-debt baseline signals are measurable.
- [x] Screenshot capture records both full-window and active-surface PNGs.
- [x] Capture environment is recorded in `manifest.json`.
- [x] Normal application startup is unchanged.
- [x] Runtime screenshot artifacts are excluded from Git.
- [x] Inventory behavior is covered by automated tests.
- [x] Baseline procedure and review protocol are documented.

## Non-goals

UI-PROD-00 intentionally does **not**:

- change colors, typography, spacing, icons, navigation or page layouts;
- consolidate the design system;
- migrate legacy widgets;
- modify services, database models or business workflows;
- claim that a screenshot generated on a CI/headless runner is equivalent to a Windows reference capture.
