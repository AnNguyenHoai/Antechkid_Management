# TEACHER-1.0 — CURRENT CODEBASE & ARCHITECTURE AUDIT

## 1. Scope

Audit performed against the current uploaded codebase:

- Teacher models
- Repositories
- Services
- Teacher Workspace UI
- MainWindow / global write integration
- Collaboration and transaction integration
- Event architecture
- Assignment domain
- Document storage lifecycle
- Timeline
- Tests

This task is an audit only. No production behavior is changed.

---

# 2. Executive Summary

## Overall status

Teacher Workspace has a substantial amount of functionality and is not a skeleton:

- Teacher CRUD
- Teacher detail
- Search/filter/sort
- Soft archive / restore at service level
- Bulk archive
- Teacher ↔ Class assignment
- Teacher documents
- Teacher timeline
- Dashboard
- Global write-mode integration through MainWindow

However, Teacher Workspace is architecturally behind the newer Student Workspace in several important areas.

### Most important findings

1. **Teacher writes are globally gated, but Teacher Workspace does not participate in the explicit transaction event/dirty architecture used by Student.**
2. **Teacher services mutate DB directly and do not publish Teacher domain events.**
3. **Teacher Documents are not write-mode safe: upload/delete controls are not disabled by `set_write_enabled()`.**
4. **Teacher list/detail code calls `notification_service.notify(...)`, but the workspace shell currently passes `None` as notification_service.**
5. **Teacher Documents Widget and Teacher Assignment Dialog create their own DB engine/session inside UI code.**
6. **TeacherAssignment is only a simple many-to-many link and has no assignment role or lifecycle.**
7. **Teacher archive is soft-delete, but there is no complete visible archived/restore workflow in the audited Teacher UI.**
8. **No dedicated teacher test files were found in the current `tests/` tree.**

```text
MainWindow
    │
    ├── Global WriteTransactionManager
    │       └── Global collaboration/write authority
    │
    └── TeacherWorkspaceShell
            ├── TeacherDashboardPage
            ├── TeacherListPage
            └── TeacherDetailPage
                    ├── TeacherFormDialog
                    ├── TeacherAssignmentDialog
                    ├── TeacherDocumentsWidget
                    └── TeacherTimelineWidget
```

Service layer:

```text
TeacherService
TeacherAssignmentService
TeacherDocumentService
TeacherTimelineService
```

Current write path:

```text
Global write mode enabled
        ↓
Teacher UI checks CollaborationManager.ensure_write()
        ↓
Service mutates DB directly
        ↓
session.commit()
        ↓
(optional) Teacher timeline entry
```

This means Teacher Workspace is **partially integrated with the global write model**, but not with a formal Teacher mutation event contract.

# 5. Write Transaction & Collaboration Audit

## Current finding: PARTIALLY INTEGRATED

MainWindow creates and owns the global `WriteTransactionManager`.

Teacher Workspace receives:

- `platform_context`
- `collaboration_manager`

MainWindow also calls `set_write_enabled()` across workspaces.

Teacher List and Detail explicitly check:

```text
collaboration_manager.ensure_write()
```

before:

- add
- edit
- archive
- bulk archive

Therefore Teacher CRUD is not simply unrestricted direct CRUD.

## But the architecture differs from Student

Teacher Workspace currently has no evidence of:

- TeacherCreated domain event
- TeacherUpdated domain event
- TeacherArchived domain event
- TeacherAssignmentChanged domain event
- TeacherDocumentChanged domain event
- `dirty_teacher_ids`
- aggregate mutation tracking

### Conclusion

Teacher Workspace participates in the **global write authority**, but does not have the newer **domain mutation/event tracking architecture**.

For Teacher's current business needs, dirty tracking is not automatically required unless Teacher later has post-publish artifacts such as reports. However, explicit mutation events are needed if other modules must reliably react to Teacher changes.

# 6. Critical UI / Runtime Findings

## GAP-T1 — Document write gating is incomplete

`TeacherDetailPage.set_write_enabled()` attempts to propagate write mode to `documents_widget`.

However, `TeacherDocumentsWidget` has no `set_write_enabled()` implementation.

Therefore:

- Upload button is not automatically disabled.
- Delete buttons are not automatically disabled.

This is a functional write-authority gap.

### Severity: HIGH

---

## GAP-T2 — notification_service may be None

Teacher Workspace Shell constructs List/Detail pages with:

```text
notification_service=None
```

But List/Detail write-denial paths call:

```text
self._notification_service.notify(...)
```

If a user attempts a write action without permission, this can cause a runtime `AttributeError` instead of a user notification.

### Severity: HIGH

---

## GAP-T3 — UI creates DB engine/session directly

### TeacherDocumentsWidget

The UI directly imports:

- `create_production_engine`
- `sessionmaker`
- `TeacherRepository`

to obtain `teacher_code`.

### TeacherAssignmentDialog

The UI directly creates a production engine/session and uses `ClassRepository`.

### Why this is a problem

The dependency direction becomes:

```text
UI → DB Engine → Session → Repository
```

instead of:

```text
UI → Service → Repository
```

This bypasses application composition, makes testing harder, and risks DB/session inconsistencies.

### Severity: HIGH

# 7. Teacher Lifecycle Audit

Current service supports:

```text
Create
Update
Archive (soft delete via deleted_at)
Restore
```

Repository active lists filter:

```text
deleted_at IS NULL
```

### Gap

The audited Teacher UI prominently supports archive, but no complete archived-teacher browsing/restore flow was found.

The model also has:

```text
status = ACTIVE
```

plus soft archive through:

```text
deleted_at
```

These are two different lifecycle concepts:

```text
ACTIVE / INACTIVE
```

and

```text
NOT ARCHIVED / ARCHIVED
```

The business meaning must be clarified and then enforced consistently.

### Severity: MEDIUM

---

# 9. Document Storage Audit

Current behavior:

```text
source file
    ↓
copy to teacher attachment folder
    ↓
create TeacherDocument DB row
```

Delete:

```text
delete physical file
    ↓
delete DB row
```

### Risks

1. Upload DB failure can leave an orphan file.
2. Physical file is deleted before DB commit in delete flow; DB failure can leave an inconsistent DB record pointing to a missing file.
3. Teacher archive does not explicitly define document retention behavior.

### Severity: MEDIUM

# 12. Recommended Roadmap

## TEACHER-1.1 — Write Safety & Dependency Cleanup

Fix first:

1. Teacher Documents must obey write mode.
2. All Teacher UI write actions must be safe when write is denied.
3. Replace `None` notification service usage.
4. Remove direct DB engine/session creation from Teacher UI.

This is the recommended next task.

---

## TEACHER-1.2 — Teacher Service Event Contract

Introduce explicit events for:

- TeacherCreated
- TeacherUpdated
- TeacherArchived
- TeacherRestored
- TeacherAssignmentChanged
- TeacherDocumentChanged

Do not add dirty tracking automatically unless there is a concrete post-publish consumer.

---

## TEACHER-1.3 — Lifecycle & Assignment Rules

Define:

- ACTIVE vs INACTIVE vs ARCHIVED
- assignment rules for inactive/archived teacher
- archive/restore UI
- class assignment validity

---

## TEACHER-1.4 — Document Storage Hardening

Make physical file and DB lifecycle safer:

```text
copy file
→ DB commit
→ finalize

or rollback cleanup on DB failure
```

Delete should avoid permanent inconsistency if DB commit fails.

---

## TEACHER-1.5 — Test Foundation

Add dedicated tests before larger feature work:

- TeacherService lifecycle
- assignment
- documents
- timeline
- write gating
- archive/restore
- UI dependency contracts

---

# 13. Final Recommendation

Teacher Workspace should not yet be rebuilt to copy Student Workspace.

The immediate need is **not a full WriteTransaction rewrite**.

The current architecture already has global write authority through MainWindow and CollaborationManager. The most urgent problems are:

```text
Write safety gaps
+ UI dependency violations
+ missing Teacher test coverage
```

Therefore the next implementation task should be:

# TEACHER-1.1 — WRITE SAFETY & DEPENDENCY CLEANUP

Scope:

```text
TeacherDocumentsWidget
TeacherAssignmentDialog
TeacherListPage
TeacherDetailPage
Teacher Workspace service boundaries
```

After TEACHER-1.1 is stable, move to lifecycle/event contracts.
